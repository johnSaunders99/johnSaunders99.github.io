Java 接口幂等：补打和重试怎么区分？

工单已经建好，回包却丢了。客户端把“补打一份”再发一遍，服务端应该把刚才的工单号还给它。换一种情况：客户拿到账单，发现纸印歪了，确实想再要一份。这回就该建新工单。

两种情况下，账单号和份数完全一样。要区分它们，幂等键得标识哪一次补打申请，而不是哪一张账单。

先约定：什么算同一次申请？

用户确认补打时，调用方生成一个键，记作 R-7。先把它保存下来，再发请求。这样即使没收到响应，客户端手里没有工单号，也还有 R-7 可用。

在同一租户下，这个接口有三种答复：

  • 第一次收到 R-7：建单，返回 201 和新工单号。
  • 又收到 R-7，还是账单 B-17、一份：返回 200 和原工单号，不另建单。
  • 仍用 R-7，份数却变成了两份：返回 409，原申请不动。

纸印歪了要再补一份呢？那是新申请，用新键 R-8。反过来，如果客户端每次超时都换新键，再严的唯一约束也拦不住重复建单。Amazon Builders’ Library 讨论过同一个取舍：让调用方表明意图，不让服务端从两份相似的请求里猜。

让数据库裁决，不靠「先查一下」

job_id 用来找工单，(tenant_id, request_key) 用来找申请。把两个标识放在同一行，就不必担心防重记录写好了，工单却没建成。接到真实接口里时，租户应从认证上下文取；不同租户碰巧用了同一个键，不能查到对方的工单。

Java 代码直接用 PreparedStatement 执行 INSERT。插入成功就返回新 ID。只有 H2 报唯一键冲突（SQLState 23505），才按租户和请求键查旧工单，核对 bill_ref 和 copies。查不到这笔申请就把异常抛回去；连接失败或超时，更不能当成“以前办过了”。

这个例子只有一条写入，用的是 JDBC 默认的自动提交。如果建单时还必须写审计记录或待发送事件，这几笔就要放进同一个事务，提交后才能答复“已受理”。还有个容易漏掉的细节：归档工单时把旧键也删了，迟到的重试就会变成新单。至少在允许重试的期限内，请求键、原工单号和核对用的参数都得留着。

用两条连接，让它们都先读到「不存在」

程序直接调用建单方法，status 是这个方法要返回给接口的状态码；jobs 是从 H2 内存库里查到的当前租户工单数。

第一张工单建好以后，直到换成新键 R-8，jobs 才从 1 变成 2。留意一下 changed：除了检查 409，程序还读回了 storedCopies=1。原工单的份数确实没被改掉。

最有用的是最后一行。换到一个没有工单的租户，两个线程各开一条 JDBC 连接；等它们都查完 R-7，才允许插入。两边查得都没错，当时确实没有这笔记录。但放行之后，只有一边建单成功（201），另一边取回同一个 ID（200）。两次查询都可以读到空，第二次插入却过不了唯一约束。

面试追问：那能保证只出一张纸吗？

不能。设想纸已经出来了，执行端却在登记完成之前断了电。重启后，库里还是那张工单，状态也许还是“待处理”。唯一约束管得住建单，管不住打印机。

恢复时，我会先用原来的 job_id 查回执。下游如果能按这个 ID 去重，就可以用它重发。可如果设备只会说“已接单”，说不清纸到底出没出，我宁愿把结果标成“待确认”，让人核对，也不自动再打一份。
