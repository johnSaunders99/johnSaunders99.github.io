Java 接口幂等：补打和重试怎么区分？

假设有个补打账单的接口。客户点了一次，服务端已经建好工单，响应却没回来；客户端再发一次，应该拿到原来的工单。可如果纸张损坏，客户明天明确要求再补一份，账单号和份数一模一样，这次就应该新建工单。

所以我不会在账单号上加唯一约束。要去重的是一次补打申请，不是那张账单。

先约定：什么算同一次申请？

调用方在用户确认补打时生成一个请求键，保存它，再发送请求。下面用 R-7 简写。超时重试沿用这个键；用户明确发起第二次申请，才换成 R-8。如果每次网络重试都生成新键，服务端看到的就全是新申请。

我给这个接口定三种结果：首次建单返回 201 和工单 ID；同一租户用同一键、同一参数重试，返回 200 和原来的 ID；如果还是 R-7，却把份数从 1 改成 2，返回 409，保留原工单。不能为了让重试“成功”，把一份已经受理的申请悄悄改成两份。Amazon Builders’ Library 也用“同一请求标识、不同意图”解释了为什么要保留原始参数。

让数据库裁决，不靠「先查一下」

工单本身就是受理凭证，不必先写一张防重表，再想办法和工单保持同步。job_id 标识工单；另一条唯一约束标识申请。租户从认证上下文取得，避免两个客户碰巧用了同一个键就互相命中。

Java 处理方法先用 PreparedStatement 做 INSERT。成功就返回新 ID。若 H2 报唯一键冲突（SQLState 23505），才按租户和请求键读原行，比较 bill_ref 和 copies，决定是返回原 ID 还是报冲突。查不到对应申请，就把异常交回上层；数据库超时、连接失败也不能翻译成“已经受理”。

本例只写一行，使用 JDBC 默认的自动提交：写入工单和占用请求键是同一个数据库操作。如果改成还要写审计表或待发送事件，就要把这些写入放在同一事务里，提交成功后再告诉客户端已受理。

这项保证也有期限：如果归档时直接删掉工单行，迟到的重试又能插入。要允许客户端在某个时间窗口内重试，就至少在这个窗口里保留请求键和原工单 ID，以及用来核对的原始参数。

用两条连接，让它们都先读到「不存在」

下载实验源码 ReprintKeys.java，把它和 H2 2.3.232 驱动（Maven Central） 放在同一目录，用 JDK 21 运行。程序直接调用建单方法，打印的是该方法对应的接口状态码；只用内存数据库，不连接打印机。

以下是 2026-11-17 的实测输出。jobs 是向数据库查询到的当前租户工单数，不是请求次数。

前四行用同一个租户。第二次调用不知道第一次返回的工单 ID，只凭 R-7 和原参数就找回了它；改份数被拒绝，库里仍是一份。第四行只把键换成 R-8，账单和份数都没变，这次数据库里确实有了第二张工单。

最后一行换到空租户。两个线程各开一条 JDBC 连接，先查询同一个 R-7，等双方都读完才允许插入。bothSawEmpty=true 就是“先查再插”不够用的反例：两边都诚实地读到了空。放行后，一个拿到 201，另一个拿到 200，两边的工单 ID 相同，库里只有一行。决定结果的是唯一约束，不是哪个线程先完成查询。

面试追问：那能保证只出一张纸吗？

不能。上面的唯一约束保证的是同一次申请只建一张工单。如果打印机已经出纸，执行端却在登记完成前断电，重启后看到的仍可能是“待处理”。这和客户端丢了建单响应，是两处不同的故障。

若下游支持按工单 ID 去重，恢复时就用同一个 job_id 重发；若能按 ID 查结果，就先核对回执。真正的新补打会有新 ID。设备若只回“已接单”，无法确认是否出纸，我会把工单标成“结果待确认”，交给人工核对，而不是盲目再打一次。
