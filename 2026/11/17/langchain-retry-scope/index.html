LangChain：JSON 解析失败，该重试哪一步？

一张“导出的 PDF 打不开”的工单，要分到哪个队列？模型答 Send this to support.，人看得懂，下游程序等的却是 {"queue": "support"}。于是我给 JSON 解析器加了一次重试。结果：解析器跑了两次，模型只被调用一次，工单还是没分出去。

这不是重试没生效。它很忠实地把同一句话又读了一遍。

一对括号，决定哪几步会重跑

这条链只有三步：lookup 查询工单可以分配到的队列，model 生成回复，parse 用 LangChain 的 JsonOutputParser 解析文本。Python 里的 a | b 把 a 的输出交给 b；with_retry() 只重新调用它包住的那一段。

为了只看这对括号的影响，每组实验都从相同的两条回复开始：第一次调用模型给一句英文，第二次才给合法 JSON。设置 stop_after_attempt=2，即包括首次调用在内最多尝试两次；只重试 OutputParserException，其他异常照常抛出。

跑一次，看调用次数而不是猜

下载完整实验脚本 retry_scope.py，在同一目录打开 PowerShell。我的环境是 Python 3.11.3、langchain-core==1.8.1。脚本用本地函数代替队列查询和模型，实际运行 LangChain 的链、解析器和重试逻辑；不需要 API key。

三组运行结果：

第一行最能说明问题：parse=2、model=1。解析器接到的是已经生成好的字符串，它没有办法让上游吐出第二条回复。后两行都拿到了 support，区别在 lookup：整条链重试查了两次，只有第三种写法复用了第一次的查询结果。真实服务里，那一次可能是数据库查询，也可能是一次向量检索。

我会把重试放在哪里

如果是模型请求超时， 错误发生在模型调用里，我会在 model 上针对可重试的网络异常做有限重试。如果请求成功、返回的文本却无法解析， 异常出在 parse，但能改变输入的是 model。这时我选 (model | parse).with_retry(...)：既能接住解析异常，又能拿到一份新文本。

重新生成不等于自动纠错。上面的写法第二次仍把原提示交给模型，并不会附上“你刚才漏了 JSON”。如果模型总是给同样的自然语言，应该改输出约束，或把具体错误写进下一次提示。另一个容易漏掉的情况是 {"team": "support"}：它能被正常解析，但程序读取 queue 时仍会失败。如果缺字段也需要重新生成，就把字段校验放进重试段，并处理它实际抛出的异常。

对这张工单，我会等解析和字段校验都通过，再写入分派记录、发通知。发送失败要单独处理：如果实际已经送达，只是回执超时，再发一次就可能重复通知。选重试边界时我先问一句：哪一步能给失败的那一步一个不同的输入？ 这里的答案是模型，不是查队列。
