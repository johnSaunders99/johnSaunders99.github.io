LangChain：JSON 解析失败，该重试哪一步？

“导出的 PDF 打不开。”模型建议 Send this to support.，分派方向没错，可程序等的是 {"queue": "support"}。一句给人看的英文，到了 JSON 解析器手里就成了异常。

我先试了最顺手的写法：既然是解析器报错，就在解析器上加一次重试。结果它真跑了两遍，模型却只答了一次。两遍读的都是那句英文，当然拿不到队列名。

一对括号，决定哪几步会重跑

这条链只有三步：lookup 查有哪些队列，model 选一个，parse 用 JsonOutputParser 读它的回复。对 LangChain 的 Runnable 来说，a | b 是把 a 的输出交给 b。with_retry() 只会重跑包住的那一段，括号外的步骤不会跟着重来。

这里的 stop_after_attempt=2 把第一次也算在内，失败后最多再试一次。只给 OutputParserException 这个机会，其他错误照常抛出。

跑一次，看调用次数而不是猜

为了让三种写法碰到同一道难题，我把模型换成了本地函数。每组第一次都回那句英文，只有被调用第二次才给合法 JSON。队列查询也在本地完成，链、解析器和重试用的都是 LangChain。给三步各加一个计数器，结果是：

第一行里，parse=2，model=1。解析器拿到的始终是同一个字符串，脚本里准备好的第二条回复根本没用上。

后两行都拿到了 support，但我会选 pair。它让模型重新回答一次，又省下了第二次 lookup。例子里多查一次几乎没代价；换成数据库查询或向量检索，没必要为了一个 JSON 格式错误连资料也重新找一遍。

我会把重试放在哪里

我先分清两种失败。如果是模型请求超时，回复都没拿到，那就只在 model 上针对可重试的网络异常再试。如果是回复到了、格式却不对，光动 parse 没用；像这个例子一样，把生成和解析一起包起来才有机会换个答案。

还有个容易忽略的细节：重试会把原提示再发一次，不会替你补一句“上次不是 JSON”。如果模型总爱回自然语言，就该改输出约束，或在下一次提示里说明具体错在哪儿。反过来，{"team": "support"} 明明是合法 JSON，照样取不出 queue。想让缺字段也触发重新生成，就得把字段校验放进括号，并处理它实际抛出的异常。

至于写分派记录、通知客服，都放到括号外面，等队列名校验通过再做。模型可以多答一次；一条可能已经送达的通知，要不要重发，是另一件事。
